# عروض مدينتي — Madinty Offers (MVP v0.1)

هذا كود فعلي قابل للتشغيل يطبّق **المرحلة A** بالكامل من الخطة، بالإضافة إلى
أساسيات أكواد الخصم وتتبعها (جزء من المرحلة B) لأن نموذج البيانات يعتمد عليها.

بدلاً من بناء الورك‌فلو داخل n8n (عمل بصري بطيء يصعب اختباره هنا)، تم تنفيذ
نفس المنطق مباشرة بكود بايثون حتى يكون لديك MVP يعمل فوراً بعد إدخال المفاتيح.
قاعدة البيانات (PostgreSQL) هي نفسها المخطط لها بالضبط، لذلك لاحقاً يمكن ربط
n8n بنفس الجداول بسهولة إن أردت الانتقال إليه دون أي تغيير في البيانات.

## المحتوى

| الملف | الوصف |
|---|---|
| `schema.sql` | مخطط قاعدة البيانات (9 جداول) + بيانات أولية (مدن/فئات) |
| `db.py` | طبقة الوصول لقاعدة البيانات (asyncpg) |
| `ai.py` | استخراج بيانات الحملة + توليد نص الإعلان (OpenAI) |
| `bot.py` | منطق البوت الكامل (تدفق المستخدم، التاجر، الإدارة) |
| `requirements.txt` | مكتبات بايثون المطلوبة |
| `.env.example` | نموذج متغيرات البيئة |

## خطوات التشغيل

### 1) قاعدة البيانات
```bash
createdb madinty
psql madinty -f schema.sql
```

### 2) البيئة الافتراضية والمكتبات
```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

### 3) متغيرات البيئة
```bash
cp .env.example .env
# ثم عدّل .env بالقيم الحقيقية:
# - TELEGRAM_BOT_TOKEN من @BotFather
# - DATABASE_URL برابط قاعدة بياناتك
# - OPENAI_API_KEY من platform.openai.com
# - ADMIN_TELEGRAM_IDS: معرّفك في تيليجرام (احصل عليه من @userinfobot)
```

### 4) التشغيل
```bash
python bot.py
```

## تدفق الاستخدام

**العميل:** `/start` ← أبحث عن عروض ← اختيار المدينة ← اختيار الاهتمامات ← تأكيد.

**التاجر:** `/start` ← صاحب نشاط تجاري ← تسجيل النشاط (اسم، نوع، مدينة، هاتف) ←
➕ إنشاء حملة ← يكتب وصفاً حراً للعرض ← الذكاء الاصطناعي يستخرج البيانات
ويولّد نص الإعلان ← معاينة ← "إرسال للمراجعة" (الحملة تبقى `pending_review`
ولا تُنشر تلقائياً أبداً).

**الإدارة (أنت):**
- `/pending` — عرض الحملات بانتظار المراجعة.
- `/approve_123` أو `/reject_123` — اعتماد/رفض حملة رقم 123.
- `/send_123` — نشر حملة معتمدة على كل المستخدمين المطابقين للمدينة/الفئة،
  على دفعات من 50 (قابل للتعديل في `.env`) لتفادي حدود Telegram.
- `/report_123` → استخدم `/report 123` — تقرير مختصر (عدد الإرسال، النقر،
  الأكواد، الاستخدام، معدل التحويل).

**العميل عند استلام الإعلان:** يضغط زر "🎁 احصل على كود الخصم" فيولَّد كود
فريد له، ويقدّمه للتاجر عند الشراء.

**التاجر عند استخدام الكود:** `/redeem KHART-8F21` لتفعيل الكود وتسجيله كمُستخدم
لأغراض التقرير.

## ملاحظات مهمة

- **لا نشر تلقائي أبداً** — كل حملة تمرّ إجبارياً بمراجعة بشرية (`/approve`/`/reject`)
  قبل أي إرسال، تماماً كما في المخطط الأصلي (البند 14).
- الإرسال دفعات (queue) وليس دفعة واحدة، لتفادي حظر تيليجرام (البند 16).
- الأسعار والباقات (Basic/Pro/VIP) لم تُبرمج بعد بقصد — كما هو موصى به في
  الخطة الأصلية (اجمع بيانات 10–20 تاجر أولاً قبل تسعير أي شيء).
- الخطوات التالية المنطقية: نشاطات جديدة تحتاج موافقة أدمن أيضاً (`businesses.status`
  موجود بالفعل بالمخطط جاهزاً لهذا)، ولوحة ويب للإدارة بدل أوامر تيليجرام،
  ونظام باقات ودفع (المرحلة B).

## لماذا Python مباشرة وليس n8n الآن؟

القرار المعماري (Telegram + n8n + PostgreSQL + OpenAI) لا يزال هو الأصح
للتوسع لاحقاً، لكن تجميع نفس المنطق داخل n8n بصرياً يستغرق وقتاً طويلاً ويصعب
اختباره تلقائياً في هذه الجلسة. هذا الكود يعطيك نسخة تعمل فعلياً اليوم بنفس
قاعدة البيانات المخطط لها بالضبط — لاحقاً يمكن نقل أي جزء (مثلاً "الإرسال
على دفعات" أو "معالجة AI") إلى n8n workflow يقرأ/يكتب من نفس الجداول، دون أي
تغيير في المخطط أو في منطق العمل.
