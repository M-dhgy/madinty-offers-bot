# عروض مدينتي — Madinty Offers (MVP v0.1)

هذا كود فعلي قابل للتشغيل يطبّق **المرحلة A** بالكامل من الخطة، بالإضافة إلى
أساسيات أكواد الخصم وتتبعها (جزء من المرحلة B) لأن نموذج البيانات يعتمد عليها.

بدلاً من بناء الورك‌فلو داخل n8n (عمل بصري بطيء يصعب اختباره هنا)، تم تنفيذ
نفس المنطق مباشرة بكود بايثون حتى يكون لديك MVP يعمل فوراً بعد إدخال المفاتيح.
قاعدة البيانات (PostgreSQL) هي نفسها المخطط لها بالضبط، لذلك لاحقاً يمكن ربط
n8n بنفس الجداول بسهولة إن أردت الانتقال إليه دون أي تغيير في البيانات.

## المحتوى

| الملف | الوصف |
|---|---|
| `schema.sql` | مخطط قاعدة البيانات الأساسي + بيانات أولية (مدن/فئات) |
| `migrations/` | ترقيات SQL مرقّمة، تسجّل إصداراتها في `schema_migrations` |
| `db.py` | طبقة الوصول لقاعدة البيانات (asyncpg) |
| `ai.py` | استخراج بيانات الحملة + توليد نص الإعلان (OpenAI) |
| `bot.py` | منطق البوت الكامل (تدفق المستخدم، التاجر، الإدارة) |
| `campaign_broadcast.py` | مسار موحد للبث الآمن المتدرج ومنع تشغيل الحملة مرتين |
| `marketplace.py` | آلة الحالات الوحيدة لسوق الأفراد |
| `tests/` | اختبارات قواعد الموافقة والاستهداف والبث |
| `requirements.txt` | مكتبات بايثون المطلوبة |
| `.env.example` | نموذج متغيرات البيئة |

## خطوات التشغيل

### 1) قاعدة البيانات
```bash
createdb madinty
psql madinty -f schema.sql
```
يُشغّل البوت الترحيلات المرقّمة مرة واحدة وبمعاملة لكل ترحيل. لا يُحذف أي سجل
تلقائيًا؛ إذا وُجدت أكواد قديمة مكررة تمنع قيد التفرد، يتوقف الترحيل برسالة
تطلب مراجعة التكرارات يدويًا بدل إسقاطها أو تجاهل القيد.

### 2) البيئة الافتراضية والمكتبات
```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

للتطوير وتشغيل الاختبارات ثبّت أيضًا `pip install -r requirements-dev.txt`.
تتطلب اختبارات PostgreSQL قاعدة اختبار منفصلة ينتهي اسمها بـ `_test`؛ مثال:
```bash
createdb madinty_test
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/madinty_test pytest -q
```
يحمّل اختبار التكامل `schema.sql` ويشغّل الترحيلات المرقّمة تلقائيًا؛ كما يختبر
ترقية مخطط سابق وإعادة تنفيذ الترحيل وحالة التكرارات داخل مخططات مؤقتة. لا تستخدم
رابط قاعدة الإنتاج للاختبارات. GitHub Actions يشغّل PostgreSQL 16 ويضبط
`DATABASE_URL` تلقائيًا؛ أما الاختبارات الوحدوية فتظل قابلة للتشغيل دون قاعدة بيانات.

### 3) متغيرات البيئة
```bash
cp .env.example .env
# ثم عدّل .env بالقيم الحقيقية:
# - TELEGRAM_BOT_TOKEN من @BotFather
# - DATABASE_URL برابط قاعدة بياناتك
# - GROQ_API_KEY من console.groq.com
# - ADMIN_TELEGRAM_IDS: معرّفك في تيليجرام (احصل عليه من @userinfobot)
```

### 4) التشغيل
```bash
python bot.py
```

إذا كان المشروع مربوطًا بـ Railway، ضع هذه القيم في تبويب **Variables** داخل خدمة
البوت، ولا تضعها داخل GitHub أو داخل الكود. بعد حفظ المتغيرات أعد النشر من Railway.

المتغيرات الاختيارية هي `GROQ_MODEL` و`GROQ_BASE_URL` و`AI_TIMEOUT_SECONDS` و
`BROADCAST_BATCH_SIZE` و`BROADCAST_BATCH_DELAY`.

## تدفق الاستخدام

**العميل:** `/start` ← أبحث عن عروض ← اختيار المدينة ← اختيار الاهتمامات ← تأكيد.

**سوق الأفراد:** يختار البائع المدينة التي يوجد فيها الغرض قبل الإرسال للمراجعة؛ ويختار المشتري مدينة البحث أو كل المدن. يظهر رقم التواصل الذي أدخله البائع ضمن تفاصيل الإعلان. تبدأ مدة الإعلان البالغة 72 ساعة عند اعتماده، ولا تنتهي الإعلانات وهي بانتظار المراجعة. إذا رُفض إعلان، يمكن لصاحبه تعديل بياناته وصورته وإعادة تقديمه عبر `/editlisting رقم_الإعلان`.

صور إعلانات الأفراد محفوظة في Telegram وتُخزّن في قاعدة البيانات كمراجع للصور فقط؛ تُمسح هذه المراجع عند انتهاء الإعلان لتفادي تراكمها.

مسودات الحملات والإعلانات غير المرسلة محفوظة في ذاكرة جلسة البوت فقط: التنقل
داخل المحادثة يتيح استئنافها بالمفتاح نفسه، لكن إعادة تشغيل البوت تفقد المسودة
غير المرسلة. بعد حفظ العملية، تبقى إعادة المحاولة في الجلسة نفسها مرتبطة بمفتاح
الإرسال ذاته حتى لا تنشئ سجلًا جديدًا عند انتهاء مهلة الرد. إذا بدأ المستخدم
مسودة أخرى بينما توجد معاينة غير مرسلة، يُطلب منه استئناف القديمة أو تأكيد
إلغائها أولًا. زر الإلغاء يمسح بيانات المسودة غير المرسلة في القسم الحالي فقط؛
لا يغيّر إعلانًا محفوظًا ولا يمسح مسودة من قسم آخر.

**التاجر:** `/start` ← صاحب نشاط تجاري ← تسجيل النشاط (اسم، نوع، مدينة، هاتف) ←
انتظار اعتماد النشاط من الإدارة ← ➕ إنشاء حملة ← يكتب وصفاً حراً للعرض ← الذكاء الاصطناعي يستخرج البيانات
ويولّد نص الإعلان ← معاينة ← "إرسال للمراجعة" (الحملة تبقى `pending_review`
ولا تُنشر تلقائياً أبداً).

**الإدارة (أنت):**
- من لوحة الإدارة ← **نشاطات بانتظار المراجعة** لاعتماد النشاط أو رفضه.
- `/pending` — عرض الحملات بانتظار المراجعة.
- `/approve_123` أو `/reject_123` — اعتماد/رفض حملة رقم 123.
- `/send_123` — نشر حملة معتمدة على كل المستخدمين المطابقين للمدينة/الفئة،
  على دفعات من 50 (قابل للتعديل في `.env`) لتفادي حدود Telegram.
- `/resume 123` — استئناف الحملة المتوقفة بعد مهلة العامل؛ يعالج المستلمين الذين لم تبدأ محاولتهم فقط.
- `/report_123` → استخدم `/report 123` — تقرير مختصر (عدد الإرسال، النقر،
  الأكواد، الاستخدام، معدل التحويل).

يحفظ البوت حالة كل مستلم قبل وبعد طلب Telegram. `RetryAfter` يُعاد بعد الانتظار
حتى ثلاث مرات؛ الرفض الصريح (`BadRequest`/`Forbidden`) لا يُعاد، والمهلة أو خطأ
الشبكة يُسجل نتيجةً ملتبسة ويُستثنى من الاستئناف التلقائي. لا يوفر `sendMessage`
مفتاح idempotency، لذلك لا يمكن ضمان exactly-once للرسائل الخارجية: قد تكون
رسالة قد وصلت رغم فقد الرد. عند تعطل العامل أثناء الإرسال، تُحوّل حالته إلى
`uncertain` بدل تكرارها. أما انتقال المستلم إلى `sent` وتسجيل حدث التقرير فهما
معاملة PostgreSQL واحدة؛ وتعذر إنهاء الحملة لا يعيد إرسال المستلمين المؤكدين.

**العميل عند استلام الإعلان:** يضغط زر "🎁 احصل على كود الخصم" فيولَّد كود
فريد له، ويقدّمه للتاجر عند الشراء.

**التاجر عند استخدام الكود:** `/redeem KHART-8F21` لتفعيل الكود وتسجيله كمُستخدم
لأغراض التقرير.

## ملاحظات مهمة

- **لا نشر تلقائي أبداً** — كل حملة تمرّ إجبارياً بمراجعة بشرية (`/approve`/`/reject`)
  قبل أي إرسال، تماماً كما في المخطط الأصلي (البند 14).
- النشاطات الجديدة تبقى `pending` مهما كانت قيمة `is_paid`؛ إنشاء الحملة واعتمادها وبثّها
  تشترط نشاطًا معتمدًا، ومدينة نشطة تطابق مدينة النشاط، وفئة نشطة.
- الإرسال دفعات ويبدأ بقفل ذري للحملة وسجل ثابت للمستلمين. `/resume` يعالج المستلمين
  `pending` فقط؛ وبعد خمس دقائق من غياب نبض العامل تُحوّل المحاولة التي بقيت `sending`
  إلى `uncertain` ولا تعاد. إذا لم يوجد مستلمون مطابقون، تُعاد الحملة إلى الاعتماد.
- المشاهدة اليومية معرفة حسب تاريخ UTC: المستخدم المعروف يسجل مشاهدة واحدة لكل إعلان
  في اليوم، أما المشاهد المجهول فتُسجل كل مرة لأن هويته غير متاحة. حُميت الكتابة
  المتزامنة بقفل PostgreSQL من دون قيد فريد جديد أو إعادة كتابة السجلات التاريخية.
- إعادة تسليم update_id نفسه لزر التواصل لا تكرر الحدث أو إشعار المعلن؛ أما ضغطات جديدة
  ذات update_id مختلف فتظل أحداثًا منفصلة كما في السلوك الحالي. لم يُضف حد أو حظر تجاري
  للضغطات؛ لذلك قد يصل إشعار جديد للمعلن عن كل ضغطة جديدة على إعلان السوق.

## التحسينات المنفذة والمقترحات

1. **مراجعة النشاطات التجارية — منفّذ:** يبدأ كل نشاط جديد بحالة `pending`، ولا
   يستطيع صاحبه إنشاء حملات قبل اعتماد الإدارة.
2. **مراجعة الحملات قبل النشر — منفّذ:** لا تُرسل أي حملة تلقائيًا؛ تعتمدها الإدارة
   أولًا ثم تبدأ عملية البث.
3. **بث آمن وموجّه — منفّذ:** تُرسل الحملات على دفعات إلى العملاء النشطين المطابقين
   للمدينة والفئة، مع منع تشغيل الحملة مرتين بالتوازي.
4. **رفع الاعتمادية والتوسع — جارٍ/تالٍ:** توجد اختبارات آلية لمسارات الموافقة
   والاستهداف والبث وسوق الأفراد، بما في ذلك اختيار المدينة وإعادة تقديم الإعلانات
   المرفوضة؛ والخطوة التالية المقترحة لوحة ويب للإدارة بدل الاعتماد على أوامر تيليجرام فقط.
5. **الباقات والدفع — بعد التحقق من الطلب:** تسجيل الأنشطة وإنشاء الحملات وإرسالها
   للمراجعة **مجاني حاليًا خلال فترة الإطلاق المحدودة فقط**. تُجمع ملاحظات التجار
   وبيانات الاستخدام — ويفضل من 10–20 تاجرًا — قبل تحديد أسعار أو باقات مثل
   Basic/Pro/VIP وإضافة الدفع. لا توجد باقات مدفوعة أو مدفوعات مفعّلة الآن، ويجب
   الإعلان عن أي أسعار وموعد انتهاء المجانية مسبقًا.

## لماذا Python مباشرة وليس n8n الآن؟

القرار المعماري (Telegram + n8n + PostgreSQL + OpenAI) لا يزال هو الأصح
للتوسع لاحقاً، لكن تجميع نفس المنطق داخل n8n بصرياً يستغرق وقتاً طويلاً ويصعب
اختباره تلقائياً في هذه الجلسة. هذا الكود يعطيك نسخة تعمل فعلياً اليوم بنفس
قاعدة البيانات المخطط لها بالضبط — لاحقاً يمكن نقل أي جزء (مثلاً "الإرسال
على دفعات" أو "معالجة AI") إلى n8n workflow يقرأ/يكتب من نفس الجداول، دون أي
تغيير في المخطط أو في منطق العمل.
